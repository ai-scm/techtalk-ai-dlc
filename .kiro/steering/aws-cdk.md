# AWS CDK Steering

## Purpose

This document defines the implementation standards for all AWS infrastructure generated with AWS CDK.

The purpose of this document is not to describe the cloud architecture itself.

Instead, it defines **how infrastructure code must be written**.

All generated infrastructure must follow these conventions.

These rules are mandatory unless explicitly overridden.

---

# Primary Technology

Infrastructure must use:

- AWS CDK v2
- TypeScript
- Node.js LTS
- npm

Do not generate infrastructure using:

- CloudFormation templates
- Terraform
- Pulumi
- AWS Console configuration

Infrastructure is always defined using AWS CDK.

---

# Infrastructure Philosophy

The CDK application must be:

- deterministic
- reproducible
- modular
- testable
- reusable

Infrastructure should behave like application code.

The CDK project should follow software engineering best practices.

---

# Repository Layout

The infrastructure project must follow this structure.

infra/

    cdk/

        bin/

            app.ts

        lib/

            networking/

            eks/

            ecr/

            database/

            monitoring/

            pipeline/

            security/

            shared/

        config/

        test/

        package.json

        tsconfig.json

Every infrastructure domain should live in its own directory.

Avoid large flat folders.

---

# CDK Entry Point

The application entry point belongs in:

bin/app.ts

The entry point is responsible only for:

- loading configuration
- selecting environment
- instantiating stacks

Business logic must never exist inside app.ts.

---

# Stack Responsibilities

Stacks define deployment boundaries.

Stacks are NOT reusable components.

Stacks should only:

- instantiate Constructs
- wire dependencies
- expose outputs

Business logic belongs inside Constructs.

---

# Construct Responsibilities

Constructs represent reusable infrastructure modules.

Examples:

VpcConstruct

EksConstruct

PipelineConstruct

DatabaseConstruct

MonitoringConstruct

Constructs should encapsulate all AWS resources required for one logical capability.

Constructs must be reusable.

---

# Construct Design

Constructs must:

accept Props

↓

create resources

↓

expose interfaces

Avoid environment lookups.

Avoid reading process.env inside Constructs.

Always use strongly typed Props.

---

# Properties

Every Construct should expose a Props interface.

Example:

VpcConstructProps

EksConstructProps

DatabaseConstructProps

Avoid passing primitive values individually.

Group configuration into Props objects.

---

# Dependency Injection

Dependencies should be injected.

Do not instantiate unrelated Constructs internally.

Preferred:

PipelineConstruct

↓

receives

↓

EcrConstruct

↓

EksConstruct

↓

VpcConstruct

Avoid hidden dependencies.

---

# Environment Configuration

Environment configuration belongs inside:

config/

Example:

local.ts

test.ts

production.ts

Each environment should export a typed configuration object.

Avoid scattered constants.

---

# Resource Naming

Resource names must be deterministic.

Preferred format:

dog-keeper-{environment}-{resource}

Examples:

dog-keeper-test-ecr

dog-keeper-test-rds

dog-keeper-test-eks

dog-keeper-prod-ecr

Avoid autogenerated names whenever practical.

---

# Stack Naming

Stacks should follow:

DogKeeperNetworkingStack

DogKeeperEksStack

DogKeeperDatabaseStack

DogKeeperPipelineStack

Avoid generic names.

---

# Configuration

Never hardcode:

AWS Account

Region

VPC IDs

Subnet IDs

Passwords

ARNs

Environment configuration should provide these values.

---

# Cross Stack Communication

Prefer passing Constructs and typed interfaces.

Avoid exporting values unnecessarily.

Avoid circular dependencies.

Cross-stack references should remain minimal.

---

# Constructs over Stacks

Business capabilities should be modeled as Constructs.

Deployment boundaries should be modeled as Stacks.

Never create reusable Stacks.

Reuse Constructs instead.

---

# AWS Construct Levels

Prefer:

L2 Constructs

Examples:

Vpc

Cluster

Repository

DatabaseInstance

Bucket

Use L1 Constructs only when AWS CDK does not expose an L2 implementation.

Avoid unnecessary CloudFormation-level resources.

---

# TypeScript Standards

Enable strict mode.

Prefer readonly properties.

Prefer interfaces over object literals.

Avoid the "any" type.

Use ES modules.

Follow modern TypeScript conventions.

---

# Imports

Prefer grouped imports.

Avoid wildcard imports unless required.

Imports should remain organized.

---

# Code Style

One responsibility per class.

Small methods.

Small Constructs.

Readable names.

Avoid deeply nested logic.

---

# Resource Ownership

Each Construct owns its resources.

Do not create resources in unrelated Constructs.

Example:

VpcConstruct

owns

VPC

Subnets

Routing

Security Groups

Do not create ECR repositories inside the VPC Construct.

---

# Infrastructure Domains

Infrastructure should be separated into domains.

Networking

↓

Security

↓

Container Registry

↓

Compute

↓

Database

↓

Monitoring

↓

Pipeline

Domains should remain independent whenever possible.

---

# Secrets

Never generate plaintext secrets.

Retrieve secrets from:

AWS Secrets Manager

Pass secret references to applications.

Avoid embedding credentials.

---

# IAM

Always apply least privilege.

Never generate AdministratorAccess.

Policies should include only required permissions.

Avoid wildcards.

---

# Tags

Every resource should include tags.

Required tags:

Application

Environment

Owner

ManagedBy

CostCenter (optional)

Tags should be applied consistently.

---

# Logging

Infrastructure should create:

CloudWatch Log Groups

Retention policies

Application logging configuration

Avoid unlimited log retention.

---

# Monitoring

Infrastructure should prepare:

CloudWatch Metrics

Container Insights

Health monitoring

Alarm placeholders

The platform should be observable from the beginning.

---

# EKS Standards

Always create:

Managed EKS Cluster

Fargate Profiles

OIDC Provider

IAM Roles

Do not provision EC2 worker nodes unless explicitly required.

---

# Networking Standards

The platform should create:

One VPC

Private Subnets

Public Subnets

Internet Gateway

Route Tables

Security Groups

Use at least two Availability Zones.

---

# Pipeline Standards

Infrastructure must provision:

CodeConnections

↓

CodePipeline

↓

CodeBuild

↓

Amazon ECR

↓

Amazon EKS

The pipeline itself should also be defined in CDK.

---

# Testing

Infrastructure should support:

cdk synth

↓

cdk diff

↓

cdk test

↓

cdk deploy

Generated code should be testable.

---

# Unit Testing

Infrastructure tests should validate:

Resource count

Resource properties

IAM policies

Networking

Naming

Use the AWS CDK Assertions library.

Avoid snapshot-only testing.

---

# Security Defaults

Encryption enabled whenever supported.

Private networking by default.

Secure defaults over convenience.

No public databases.

No unrestricted security groups.

---

# Cost Optimization

Prefer managed services.

Prefer Fargate.

Prefer serverless services.

Avoid idle resources.

Avoid unnecessary NAT Gateways when architecture allows alternatives.

---

# Future Extensibility

The architecture should support future additions without restructuring.

Possible future modules:

S3

Cognito

SNS

SQS

EventBridge

API Gateway

Lambda

New services should be implemented as new Constructs.

Avoid modifying unrelated modules.

---

# Non Goals

The CDK project must not:

Deploy applications

Generate Kubernetes Deployments

Manage Garden

Build Docker images

Generate Helm charts

Application deployment belongs to Garden.
