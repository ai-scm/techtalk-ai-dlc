# AWS Platform Steering

## Purpose

This document defines the architectural standards for deploying the Dog Keeper application on AWS.

These rules are mandatory for all generated infrastructure.

The objective is to ensure that every infrastructure component follows the same architecture, naming conventions, deployment strategy and operational model.

Unless explicitly stated otherwise, every AWS resource generated by Kiro must follow these rules.

---

# Guiding Principles

The cloud platform follows these principles:

- Infrastructure as Code first
- Immutable infrastructure
- Build once, deploy many
- Everything is reproducible
- Git is the source of truth
- Least privilege
- Managed AWS services over self-managed components
- Cost optimization by default
- Separation of infrastructure and application deployments

Infrastructure must never require manual configuration through the AWS Console.

Every infrastructure change must be represented as code.

---

# Infrastructure Technology Stack

The platform uses the following AWS services.

| Component | Technology |
|------------|------------|
| Infrastructure as Code | AWS CDK v2 |
| Programming Language | TypeScript |
| Source Control | GitHub |
| Source Integration | AWS CodeConnections |
| CI/CD | AWS CodePipeline |
| Build | AWS CodeBuild |
| Container Registry | Amazon ECR |
| Kubernetes | Amazon EKS |
| Compute | AWS Fargate |
| DNS | Amazon Route53 |
| Secrets | AWS Secrets Manager |
| Monitoring | Amazon CloudWatch |
| Logging | CloudWatch Logs |

No alternative technologies should be generated unless explicitly requested.

---

# Infrastructure Ownership

Infrastructure and applications have different responsibilities.

## AWS CDK

AWS CDK owns:

- VPC
- IAM
- Route53
- ECR
- EKS
- Fargate Profiles
- CloudWatch
- Secrets Manager
- CodePipeline
- CodeBuild
- Networking
- Security Groups

Garden must never create these resources.

---

## Garden

Garden owns only application deployment.

Garden is responsible for:

- Kubernetes Deployments
- Services
- Ingress
- ConfigMaps
- Secrets references
- Sync
- Development workflow
- Application lifecycle

Garden must not provision AWS infrastructure.

# Stack Organization

Infrastructure must be separated into logical stacks.

Preferred layout:


ContainerRegistryStack

↓

EksStack

↓

MonitoringStack

↓

PipelineStack

↓

ApplicationStack

Each stack must have a single responsibility.

Large monolithic stacks should never be generated.

---

# AWS CDK Standards

Infrastructure must use:

- AWS CDK v2
- TypeScript
- Constructs
- Strong typing
- Reusable components

CloudFormation templates must never be written manually.

---

# Environment Strategy

The platform contains multiple environments.

Current environments:

- local
- test
- production

The architecture must support future environments.

Examples:

- development
- qa
- sandbox

Every environment should have isolated configuration.

No environment-specific values should be hardcoded.

---

# Networking

Infrastructure must be configured with:

- One VPC
- Two Availability Zones
- Public Subnets
- Private Subnets

Application workloads must execute inside private subnets whenever possible.

Public internet exposure must happen through an Application Load Balancer.

This resources must already exist, so arns must be provided.

---

# Kubernetes Platform

The Kubernetes platform is Amazon EKS.

Requirements:

- Managed Control Plane
- Managed by AWS
- Kubernetes version supported by AWS
- Infrastructure provisioned by CDK

The cluster should be reusable across environments.

---

# Compute Strategy

Application workloads must execute on AWS Fargate.

Reasons:

- No EC2 management
- Lower operational complexity
- Pay per use
- Automatic scaling
- Serverless Kubernetes

Node Groups should not be generated unless there is a documented technical limitation.

---

# Fargate Profiles

Each application namespace should have an associated Fargate Profile.

Examples:

dog-keeper-test

dog-keeper-production

Infrastructure should avoid sharing namespaces between environments.

---

# Kubernetes Restrictions

Generated workloads must avoid features unsupported by Fargate.

Do not generate:

- HostPath volumes
- Privileged containers
- DaemonSets
- Host networking
- Host PID
- Host IPC

Assume serverless Kubernetes.

---

# Container Registry

All container images must be stored in Amazon ECR.

Never push production images to DockerHub.

Image tags should follow semantic versioning whenever possible.

The same image promoted through environments must be reused.

Images must never be rebuilt between environments.

---

# Database

Database lives insisde de kubernetes cluster and is managed by helm, like in the local development environment.

---

# Secrets

Secrets must be stored in AWS Secrets Manager.

Never:

- Commit secrets into Git
- Hardcode passwords
- Store production credentials in ConfigMaps

Applications should reference Secrets Manager.

---

# Identity and Access Management

Use least privilege.

Generate dedicated IAM Roles.

Avoid wildcard permissions.

Policies should grant only required permissions.

---

# Monitoring

Infrastructure must provision:

- CloudWatch Logs
- CloudWatch Metrics
- Container Insights (optional)
- Log Groups

Application logs should be centralized.

---

# Observability

Every deployed service should expose:

- Liveness endpoint
- Readiness endpoint
- Health endpoint

Health endpoints should be consumable by Kubernetes and monitoring systems.

---

# GitHub Integration

GitHub must integrate with AWS using AWS CodeConnections.

Never use:

- Personal Access Tokens
- Static GitHub credentials

Authentication should rely on managed AWS integrations.

---

# Security

Infrastructure should default to secure configurations.

Enable encryption whenever supported.

Prefer managed encryption keys.

Resources should not be publicly accessible unless explicitly required.

---

# Naming Convention

Resources should follow predictable names.

Examples:

dog-keeper-test

dog-keeper-production

dog-keeper-ecr

dog-keeper-eks

dog-keeper-rds

Avoid autogenerated names whenever practical.

---

# Cost Optimization

Prefer managed serverless services.

Avoid idle EC2 instances.

Prefer:

- Fargate
- ECR
- CloudWatch

Avoid unnecessary infrastructure.

Infrastructure generated for demonstrations should minimize operational costs.

---

# Future Extensibility

The architecture should allow future integration with:

- Amazon Cognito
- Amazon S3
- EventBridge
- SQS
- SNS
- ElastiCache
- API Gateway

Future services should integrate without requiring architectural changes.

---

# Non Goals

This project does not generate:

- Manual AWS Console configuration
- Terraform
- Raw CloudFormation
- EC2-managed Kubernetes clusters
- Docker Swarm
- ECS

Amazon EKS is the standard Kubernetes platform.
