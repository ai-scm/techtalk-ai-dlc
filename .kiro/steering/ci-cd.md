# CI/CD Steering

## Purpose

This document defines the Continuous Integration and Continuous Delivery strategy for the Dog Keeper platform.

The objective is to guarantee that every software change follows the same promotion process from local development to production.

Every deployment generated by Kiro must follow this workflow.

These rules are mandatory.

---

# CI/CD Philosophy

The platform follows these principles.

- Build once
- Deploy many
- Immutable artifacts
- Fully automated validation
- Manual promotion to test and production
- Infrastructure as Code
- GitOps mindset
- Repeatable deployments

Production deployments must never require rebuilding application artifacts.

---

# Deployment Strategy

The application is promoted through multiple environments.

Current environments:

Local

↓

Test

↓

Production

Future environments may include:

Development

QA

Sandbox

The deployment strategy must support additional environments without architectural changes.

---

# Source of Truth

GitHub is the only source of truth.

All deployments originate from Git.

No deployment should originate from a developer workstation.

No manual uploads are allowed.

---

# Source Integration

GitHub integrates with AWS using:

AWS CodeConnections

Never use:

- Personal Access Tokens
- Static credentials
- Manual repository synchronization

Authentication should rely on managed AWS integrations.

# Source Stage

The pipeline starts after a Git push.

Supported events:

- Push
- Pull Request Merge
- Release Branch

Direct production deployments are not allowed.

---

# Build Stage

The build stage is executed by AWS CodeBuild.

Responsibilities:

- Install dependencies
- Restore cache
- Compile application
- Execute unit tests
- Build Docker images

Garden must not build container images in CI.

---

# Build Commands

Typical execution flow:

Install dependencies

↓

Lint

↓

Unit Tests

↓

Docker Build

↓

Docker Push

↓

Artifact Publication

Application-specific commands are defined by each service.

---

# Code Quality

Every build must validate:

- Formatting
- Lint
- Static Analysis
- Unit Tests

The pipeline must stop immediately if any validation fails.

---

# Container Images

Docker images are built only once.

Images are published to Amazon ECR.

Every environment must deploy the exact same image.

Images must never be rebuilt between environments.

---

# Artifact Promotion

Application promotion follows this rule.

Build

↓

Image Published

↓

Deploy Test

↓

Approve

↓

Deploy Production

Never create a second build for Production.

---

# Test Environment

Every successful build is deployed automatically to the Test environment.

Deployment command:

garden deploy test

Deployments should be automatic.

No manual intervention is required.

---

# Smoke Tests

Immediately after deployment:

Execute smoke tests.

Examples:

- Health endpoint
- Readiness endpoint
- API availability
- Frontend availability

Smoke tests validate that the deployment succeeded.

---

# Integration Tests

Integration tests execute after smoke tests.

Typical validations:

Frontend

↓

BFF

↓

Backend

↓

Database

The pipeline must stop if integration tests fail.

---

# Manual Approval

Production deployments require human approval.

Automatic deployment to Production is forbidden.

Use:

AWS CodePipeline Manual Approval Action

Approval must occur only after:

- Successful Build
- Successful Deployment to Test
- Successful Smoke Tests
- Successful Integration Tests

---

# Approval Notifications

Approval actions should publish notifications using:

Amazon SNS

Notification targets may include:

- Email
- Chat integrations
- Incident management systems

Approvers should receive deployment information before approving.

---

# Production Deployment

After approval:

garden deploy production

The deployment must reuse:

- Same Docker image
- Same artifact
- Same version

Production must never trigger a rebuild.

---

# Production Validation

After deployment execute:

- Smoke Tests
- Health Checks
- Readiness Checks

Production validation confirms deployment success.

---

# Rollback Strategy

Rollback should deploy the previously approved image.

Never rebuild an older commit.

Rollback should reference an existing image stored in Amazon ECR.

---

# Versioning

Every deployment should have:

- Git Commit
- Image Tag
- Build Number

The deployed version must be traceable.

---

# Garden Responsibilities

Garden is responsible only for:

- Deploy
- Sync
- Kubernetes lifecycle
- Environment orchestration

Garden does not:

- Build infrastructure
- Create AWS resources
- Build Docker images inside CI

---

# CDK Responsibilities

AWS CDK provisions:

- VPC
- EKS
- RDS
- ECR
- IAM
- CodePipeline
- CodeBuild
- Monitoring

CDK provisions the platform.

Garden deploys the applications.

---

# Failure Policy

Stop the pipeline immediately when:

- Build fails
- Tests fail
- Docker build fails
- Image push fails
- Deploy fails
- Smoke tests fail
- Integration tests fail

Production promotion must never continue after failures.

---

# Security

The pipeline must:

Use IAM Roles

Avoid static credentials

Use Secrets Manager

Encrypt artifacts

Apply least privilege

No credentials should exist inside the repository.

---

# Observability

The pipeline should publish:

Build Logs

Deployment Logs

Approval History

Deployment Duration

Pipeline Metrics

CloudWatch is the default monitoring platform.

---

# Cost Optimization

Avoid unnecessary executions.

Reuse Docker cache whenever possible.

Reuse previously built artifacts.

Do not execute redundant builds.

---

# Future Extensions

The pipeline should allow future integration with:

Security Scanning

Dependency Scanning

Container Vulnerability Scanning

Performance Testing

Canary Deployments

Blue/Green Deployments

Progressive Delivery

Feature Flags

These capabilities should be added without redesigning the pipeline.

---

# Non Goals

The CI/CD pipeline does not:

Provision infrastructure manually

Deploy from developer machines

Rebuild production artifacts

Bypass automated tests

Skip manual approval

Deploy unversioned images
